# インターホン音声登録・検知・録音の試作

CY8CPROTO-062-4343W の内蔵PDMマイクで呼び出し音を登録し、類似する音を検知したときの実際の音声を保存するプロジェクトです。
Wi-Fi 接続テスト（`firmware/wifi-check`）をコピーして独立させています。既存プロジェクトのソースや、基板に書き込まれているプログラムは変更していません。

## 現在の実装と確認範囲

- 内蔵マイク1チャンネル、16kHz、16bit PCMの連続取得。CPU/SDIOのクロックを変更せず、既存48MHz PLLからHFCLK1を駆動します。
- 環境音5秒 → 呼び出し音3回 → 別の1回で確認する登録フロー。
- 16帯域のログメル特徴と、時間のずれを制限したDTWによる照合。
- 登録モデルを外付けQSPIフラッシュに保存。2コピーとCRCで、更新途中の電源断から旧モデルを復元します。
- 検知した音の約1秒前から約1秒後までを保存。最大6秒、未送信録音は5件まで。
- HTTPSによるWAV送信。保存したイベントIDがACKとして返るまで、録音を再利用可能にしません。
- 受信側の参考実装とホストテストを同梱しています。

**ボード向けビルドとPC上のテストは通過。実機への書き込み・マイク録音・実際の呼び出し音の精度検証・公開サーバーへの音声送信は未実施です。**
現時点のしきい値は初期値です。合成音によるテスト結果を、実際のインターホンに対する精度保証として扱わないでください。
呼び出しの検知後、録音完了とフラッシュ保存を待ってWAVを送る初版です。即時イベント通知、iPhone通知、AI応答は今後の統合範囲です。

## ビルド

ModusToolbox 3.9 / GCC Arm 14.2.1 で確認しています。カスタムBSPの設定・生成コードを `bsps/` に含めています。
ライブラリは `deps/` の指定に基づいて取得します。同階層の `mtb_shared` に既にある場合は再利用できます。

```sh
cd firmware/psoc6
make getlibs              # 依存ライブラリが未取得の場合
make -j8 build
```

Wi-Fiの設定はこのプロジェクト専用です。既存プロジェクトの認証情報はコピーしていません。
未設定でも音声機能は動作し、Wi-Fiタスクは設定待ちになります。

```sh
python3 configure_wifi.py
```

後で実機確認するときだけ `make -j8 program` を実行します。これは基板の既存ファームウェアを置き換えます。
USBはKitProg3側のJ8、シリアルは115200 bps / 8N1です。別のシリアルモニターが同じポートを開いている場合は終了します。
ユーザーボタンはWi-Fiのhost wakeと共用なので使用せず、シリアルから操作します。

## 初回セットアップ

### 保存領域の初期化

外付けQSPIフラッシュの**末尾2MiB**を専用領域として使います。初回に勝手に消去する処理はありません。
初期化してよいことを確認してから、シリアルで以下を入力しEnterを押してください。

```text
FORMAT_AUDIO_STORAGE
```

**この操作は末尾2MiBの既存データ、登録モデル、録音を消去します。** 他用途のデータがある基板では、先に領域配置を確認してください。
保存領域を初期化しなくてもマイクは取得を続けますが、登録の開始と録音の永続保存はできません。
書き込み領域はドライバーで2MiBの範囲内に制限し、セクターの境界も検査しています。

### 音の登録

1. 室内インターホンの近くにボードを固定します。
2. `e` とEnterを入力し、5秒間静かにします。
3. シリアルの案内に合わせて、呼び出し音を3回鳴らします。各回の終了後に次の案内を待ちます。
4. 3回が十分似ていれば、確認用にもう1回鳴らします。
5. `[SETUP] Model persistence verified.` が出れば、保存内容のCRC検証まで完了です。
6. もう一度鳴らし、`[DETECTED]` と `[AUDIO] Recording saved to flash` を確認します。

電源を入れ直すと、CRCが正しい最新のモデルを読み込みます。
登録中は通常検知を休止します。`x` で登録を取り消すと、以前のモデルに戻ります。
本体位置や呼び出し音を変更した場合は登録し直します。

| シリアル入力 | 操作 |
|---|---|
| `h` | コマンド一覧 |
| `e` | 環境音測定から登録開始 |
| `x` | 登録を中止 |
| `r` | 判定を使わず5秒録音して送信待ちにする。距離値は -1 |
| `s` | モデル、判定しきい値、直近の音量（RMS）、取り込み欠落、送信設定の状態 |
| `FORMAT_AUDIO_STORAGE` | 専用保存領域を消去して初期化 |

各入力の最後にEnterが必要です。

## 音の扱いと初版の制限

- 常時保持する生音はRAMの直近6秒で、順番に上書きします。通常時の音を連続してフラッシュやサーバーへ保存しません。
- 登録時の生音は残さず、特徴列3個・判定しきい値・環境音に基づく入力レベルの基準を保存します。
- 1回の呼び出し音は0.2〜4秒が対象です。入力レベルが基準を下回る状態が0.5秒続くと区間終了とします。音の途中の間隔が長い機種では分割されるため、実測して区間判定の調整が必要です。
- 検知後は約1秒の後続音を保存し、その後さらに基準以下の音が1秒続くまで再検知を抑制します。連打の扱いは実機に合わせて調整します。
- フラッシュへの保存と送信は別タスクで動き、マイクの取得を続けます。RAM上の保存待ちは1件です。送信待ちでこのバッファが塞がっていると、新しい録音は明示的なログを出して破棄します。フラッシュ5件が埋まった場合も既存録音を上書きせず、新規録音の保存失敗を表示します。
- サーバーのACK後は論理的に削除し、その領域を次の録音で消去・再利用します。ACK直後の物理的な消去はしません。
- 取り込み欠落やFIFOオーバーフローがあれば、その時点の候補・録音を破棄します。登録中なら登録を中止します。受信が止まった場合は状態を表示し、ボードのリセットが必要です。
- CRCが不一致の録音はアップロードせず、隔離して他の録音の送信を続けます。隔離領域の回復は明示的な保存領域初期化で行います。
- 本機で登録した音をテレビ等から再生すると、音だけでは実際の呼び出しと区別できません。

## 音声アップロード

初期状態ではアップロード先とトークンが空で、音声送信は無効です。
既存のDoor APIには今回の録音保存エンドポイントがあるとは確認できていないため、推測で呼び出していません。
既存の `/health`、`/v1/status` へのGET確認処理はWi-Fi接続後に動きます。

1. 受信側に [API契約](docs/upload-api.md) に沿うエンドポイントを実装・配置します。
2. `source/upload_config.example.h` を `source/upload_config.h` にコピーします。
3. ホスト名・認証トークン・サーバー証明書に合う信頼済みルートCAを設定します。
4. 再ビルド・書き込みします。

`wifi_config.h`、`upload_config.h`、ビルド済みファームウェア、録音はGitの対象外です。
HTTPSはCA・ホスト名・有効期間を検証します。Wi-FiとNTP時刻同期が完了するまで送信しません。
失敗時は同じイベントIDで30秒後を目安に再試行します。複数件があるときは順番に試し、1件の失敗で他の送信を永久に止めないようにしています。
サーバーから `200` または `201` と該当イベントIDが返ったときだけ、ACKをフラッシュに記録します。

`tools/receiver.py` は、標準Pythonだけで動くローカル検証用の受信側実装です。既存サーバーへの変更・配置はしていません。
公開運用ではHTTPS終端、保存容量・保持期間の管理、既存アカウントとの認証連携を追加してください。

```sh
# AUDIO_RECEIVER_TOKEN をローカルで設定してから実行
python3 tools/receiver.py --directory recordings
```

127.0.0.1:8770のみで待ち受けます。ボードはHTTPS/443のみを使うため、そのまま直接は接続できません。

## 検証

```sh
sh tests/run.sh
```

Cの処理はAddressSanitizer/UndefinedBehaviorSanitizer付きで検証します。
対象は音量・長さを変えた合成音の照合、異なる音順と雑音の除外、循環バッファ、WAVヘッダー、モデル妥当性、CRC、保存途中の電源断、再起動、満杯時の上書き防止です。
Pythonテストでは認証、WAV検証、再送の重複排除、保存失敗時のACK抑止、途中で終了した保存からの回復を確認します。

次の実機検証では、まず `r` の音質と欠落数を確認し、その後に登録・検知を試します。
実際の呼び出し音の取り逃し、テレビ・会話の誤検知、送信中の取り込み、再起動後のモデル復元、Wi-Fi切断時の再送はまだ評価が必要です。

## 主なファイル

- `source/audio_core.*`: ログメル特徴、DTW、循環バッファ、WAV、CRC。
- `source/audio_store.*`: 2コピーの登録モデルと5件の録音の保存。
- `source/audio_app.c`: PDM、シリアル操作、登録・検知の状態制御、保存タスク。
- `source/door_server.c`: 既存のHTTPS確認処理とWAVアップロード。
- `tools/receiver.py`: 録音受信APIの参考実装。
- `tests/`: ホストテスト。

参考: [Infineon PDM/I2Sサンプル](https://github.com/Infineon/mtb-example-psoc6-pdm-to-i2s)、[HTTPSサンプル](https://github.com/Infineon/mtb-example-wifi-https-client)。
