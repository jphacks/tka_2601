# MONBAN ファームウェア（XIAO ESP32S3）

[![XIAO firmware](https://github.com/jphacks/tka_2601/actions/workflows/xiao-firmware.yml/badge.svg)](https://github.com/jphacks/tka_2601/actions/workflows/xiao-firmware.yml)

E84 と M5Stack に分かれていた機能を、Seeed XIAO ESP32S3（無印）1 枚で動かすファームウェアです。追加基板（MAX98357A アンプ、LMD3526 PDM マイク）を前提にしています。基板の設計データはまだこのブランチにないので、ピン配置は下の表を見てください。

**実機ではまだ一度も動かしていません。** 確かめたことと確かめていないことは「[確認の状況](#確認の状況)」に書きました。

## 実機なしで試す

XIAO がなくても、次のコマンドで試せます。リポジトリのどこからでも `bash firmware/xiao/run.sh ...` で実行できます。

| コマンド | 確かめること | 必要なもの | 時間の目安 |
|---|---|---|---|
| `bash run.sh test` | 各部のホストテストと Web UI のテスト | clang、Python 3、Node.js | 1 分 |
| `bash run.sh eval` | 合成音でチャイム検出の新旧を比べる（[チャイムの登録と検出](#チャイムの登録と検出)） | clang | 15 秒 |
| `bash run.sh wav 登録.wav 対象.wav` | 録音した WAV で、登録と検出の時刻・スコアを見る | clang | 数秒 |
| `bash run.sh e2e` | 本物の `/api/relay` のコードと、ファームウェアの通話処理をつないだ会話 | 上に加えて uv | 初回は依存の取得が要る |
| `bash run.sh browser` | 本物の Chromium で Web UI を開き、チャイム登録から通話まで実際にクリックして通す | e2e と同じ。初回は Chromium の取得（約 100 MB）が要る | 2 分 |
| `bash run.sh qemu` | ESP32-S3 用のバイナリを QEMU で起動し、シリアルで操作 | arduino-cli、Python 3 | 初回は ESP32 コアの取得（数 GB）が要る |
| `bash run.sh bench` | ブラウザで Web UI を操作する。通話まで動く | e2e と同じ | 起動まで数十秒 |
| `bash run.sh qemu ui` | ブラウザで Web UI を操作する。相手は QEMU 上の ESP32-S3 用バイナリ | qemu と同じ | 起動まで 1 分ほど |

Web UI を試す 2 つの違いは次のとおりです。`bench` は Mac 向けにコンパイルしたファームウェアで、音声は模擬なので通話まで進みます。`qemu ui` は実機用のバイナリそのものですが、QEMU に Wi-Fi と音声がないので、サーボの調整や保存までしか動きません。QEMU 自体に Web UI はなく、どちらも `http://127.0.0.1` の同じ画面を使います（`bench` は 8767 番、`qemu ui` は 8768 番）。

QEMU の本体は初回に公式リリースから `.host-build/` へ取得し、SHA-256 を照合します。対応するのは macOS と Linux です。Windows は WSL で動かしてください。

GitHub では、`firmware/xiao` に触れる PR ごとに `test`、`e2e`、`browser`、ビルド、`qemu` が自動で動きます。手で動かすときは Actions の「XIAO firmware」から Run workflow を押します。

## 機能

| 機能 | 内容 | 移植元 |
|---|---|---|
| チャイムの登録と検知 | ログメル・音程・立ち上がりの特徴と、ストリーミングの部分一致 DTW。静かに 2 秒、1 回鳴らすだけで登録し、鳴っている途中で判定する | `firmware/psoc6` を作り直した（Issue #59） |
| 登録の保存 | 2 MiB の専用パーティションに 2 つ写しと CRC で保存 | `firmware/psoc6` |
| 録音の保存と送信 | HTTPS で WAV を送り、同じイベント ID の ACK を待つ。送信先を設定したときだけ動く | `firmware/psoc6` |
| 会話 | `/api/relay` と WSS で接続。16 kHz、16 bit、モノラルの PCM を 20 ms（640 B）ごとに送受信 | `PSOC_Edge_E84` |
| 再生 | I2S で再生し、DMA が空になってから完了を報告 | `M5Stack_Basic_E84_Link` |
| サーボ | 押して戻す動作、角度と時間の調整、USB からのテスト | `M5Stack_Basic_E84_Link` |
| 確認と調整の Web UI | Mac の `calibration_ui/` が USB シリアルで本体とやり取りする | `M5Stack_Basic_E84_Link` を作り直した |

E84 と M5 の間の UDP 通知と TCP 中継（DVS1）は削除しました。通話の処理が、サーボとスピーカーを直接動かします。

初期設定では物理プッシャー1が通話開始、2が終話です。アプリの「設定 → プッシャー設定」で、通話用に1個を共有するか、2個へ別々に割り当てるかを選べます。1個では物理1・2のどちらも選べ、2個では開始・終話の担当を入れ替えられます。接続数の自動検出は行いません。

物理3は解錠用のUSBテスト・角度調整として保持し、通話からは動かしません。中継サーバーに解錠の指示がなく、`docs/spec.md` 5.6 が「鍵やドアを開ける約束をしない」と決めているためです。

## ビルドと書き込み

`arduino-cli` と esp32 コア 3.3.8 を使います。`arduino-cli` は PATH にあるものか Arduino IDE に入っているものを使い、コアがなければ初回に入れます。パーティションは `partitions.csv` のとおりで、PSRAM は OPI にしています。

```bash
bash run.sh build
```

```bash
bash run.sh upload /dev/cu.usbmodem1101
```

書き込みは XIAO 自身の USB-C から行います。追加基板の USB-C は電源専用で、書き込むときは抜いておきます。

## 設定

設定を変えたら、ビルドと書き込みをやり直します。作られるヘッダーは Git の対象外です。

Wi-Fi の設定です。iPhone のテザリングでは `--hotspot` を付けます。

```bash
python3 configure_wifi.py
```

サーバーの設定です。`.env.example` を `.env` にコピーして `DOOR_API_KEY`、`DOOR_RELAY_MODE`、`DOOR_DEVICE_KEY` を入れてから実行します。

```bash
python3 configure_api.py
```

録音の送信先は任意です。設定しない間は、録音をフラッシュに保存しません。`docs/spec.md` 5.2 と 10 章で扱いが未定のため、既定で切っています。

```bash
python3 configure_upload.py --ca /path/to/receiver-root-ca.pem
```

## 最初に動かす手順

### アプリからのプッシャー設定

アプリに保存した設定は、XIAOが待機中に取得し、本体への保存と読み戻しを確認してから反映結果を返します。通話中は割り当てを切り替えません。設定を保存しただけでは反映済みにならないため、本体への反映完了を確認してから取り付けを変更します。

本体の`.env`に`SUPABASE_URL`・`SUPABASE_PUBLISHABLE_KEY`と登録済みの`DOOR_DEVICE_KEY`を設定し、接続先の信頼するCAを指定します。

```sh
python3 configure_api.py
python3 configure_device.py --ca /path/to/trusted-root-ca.pem
bash run.sh build
```

生成した`device_config.h`はGit対象外です。設定APIの追加契約、XIAO、アプリの順に導入します。[実装・検証記録](../../docs/verification/pusher-assignment.md)に、エミュレーターで確認した範囲と未確認の実機動作を記載しています。

共有ボタンの押下中に中断・電源断が起きた場合や、共有する出力を単体テスト・プレビューした後は、親機を手動で終話してからUSB調整画面で待機状態を確認します。`@confirm`も同じ確認操作で、ボタンを押しません。再起動や割り当て変更だけでは要確認状態を解除しません。

### アプリからの動作モードと死活通信

アプリで選んだ動作モード（通常・おまかせ・外出・停止）は、待機中に15秒ごとに`GET /functions/v1/device/mode-settings`で取得します。ネットワークタスクが取得するため、チャイムの検知と通話は待たされません。通話中は取得しません。

- 取得した値は、通話中継への`mode`に使います。ビルド時の`DOOR_RELAY_MODE`は、一度も取得できていないときの初期値だけです。
- 最後に取得できた値をNVSに保存し、再起動後と通信できない間はその値で動きます。保存できなかったときも取得した値を使い、次の取得で保存を再試行します。
- 未対応の値、型や契約版が違う応答、HTTPエラー、未ペアの応答は、最後の正常値を変えません。不明な値を停止として扱うことはありません。
- 停止モードでは、チャイム検知と手動の通話要求を通話開始の前に捨てます。待たせて後から再生することはありません。通話中に切り替わっても、始まっている通話は止めません。通信確認用のAPI試験とスピーカー試験は停止モードでも使えます。
- `PUT /functions/v1/device/heartbeat`は、通信できる間60秒ごとに送ります。失敗したときは10秒から始めて60秒まで間隔を延ばして再試行し、成功した時刻だけを送信済みとして扱います。アプリの接続切れ通知は15分間heartbeatが途絶えたときです。

- `PUT /functions/v1/device/mode-status`（本文`{"mode":"normal"}`）で、本体が実際に動かしているモードをクラウドの`devices.applied_mode`へ報告します。アプリが保存した`devices.mode`とは別の値です。報告するのは、このブート中に`mode-settings`の取得が成功し、そのモードで動いているときだけです。NVSに保存された値やビルド時の`DOOR_RELAY_MODE`で動いている間は、取得が成功するまで報告しません（アプリの設定として動いているとは言えないため）。取得に成功した最初の1回は、モードが同じでも送ります。以後はモードが最後に報告に成功した値と変わったときだけ送ります。
  - 保存に失敗したモードも、実際に動いているので報告します。200以外と通信失敗は未送信として扱い、10秒から60秒までの上限つきの間隔で再試行します。新しいモードに変わったときは、古い失敗の間隔を引き継がず10秒から数え直します。取得・heartbeat・チャイムは報告の失敗に待たされません。
  - 未ペアの応答を受けたら報告済みの記録を捨て、ペアリング後に取得が成功した時点で改めて1回送ります。
  - `applied_mode_at`はクラウドが報告を受けた時刻で、本体の生存を示しません。本体との最後の通信は`last_heartbeat_at`です。
  - 実装は`device_mode_sync.c`、試験は`tests/device_mode_report_test.c`です。

同じ`device_config.h`の設定（`configure_device.py`）を使います。未設定の本体は、取得も送信もしません。

### アプリからのチャイム登録

アプリの「チャイムを登録」の依頼は、ネットワークタスクが`chime_enroll_sync_step()`で取得し、`audio_app_enroll_start()`・`audio_app_enroll_cancel()`で実行して、進捗を報告します（Issue #62、実装は`chime_enroll_sync.c`と、契約の解析・本文の作成の`chime_enroll_protocol.c`）。他の同期と同じく、通話中・通信不可・未設定のときは何も送らず、1回の呼び出しで送るリクエストは最大1件です。

| 向き | リクエスト | 内容 |
| --- | --- | --- |
| 取得 | `GET /functions/v1/device/chime-enrollment` | `{"contract_version":1,"paired":bool,"request_seq":int,"action":"start"\|"cancel"\|null}` |
| 報告 | `PUT /functions/v1/device/chime-enrollment-status` | `{"handled_seq":int,"phase":P,"reason":R,"registered":bool}` |

- 取得の間隔：登録の実行中、有効なチャイムのモデルがまだない間、未確認の報告がある間は3秒。それ以外は15秒。`paired:false`の間は5秒で取得を続け、他には何もしません。取得の失敗は5秒から60秒までの上限つきの間隔で再試行します。
- `request_seq`が処理済みより大きいときだけ動きます。同じ連番は何度取得しても再実行しません。`start`は、保存領域が使える・モデルの保存中や初期化中ではない・コマンドのキューに空きがあるときだけ`audio_app_enroll_start()`を呼び、音声タスクが2秒以内に登録を始めなければ失敗とします。どれかに当たると`phase:"failed"`・`reason:"busy"`をその連番で報告し、連番は処理済みにします（自動では再試行しません）。`cancel`は`audio_app_enroll_cancel()`の後に`cancelled`を報告します。実行中でない、または前回の失敗が残っているだけなら`cancelled`、すでに保存まで終えていれば`done`のままです。
- 報告：`audio_app_enroll_status()`の段階が変わるたびに、次のネットワークタスクの周期（200 ms）で送ります。登録の実行中（noise・listen・analyze・saving）は60秒ごとに同じ内容を再送します。idleと、終わった後の done・failed・cancelled には再送しません（終わった状態は変わらないため。契約は「idle以外」の再送としているので、この点だけ狭めています）。失敗した報告は同じ内容なら5秒から60秒の間隔で再送し、別の段階になれば待たずに送ります。`registered`は`audio_app_model_valid()`です。
- 段階の対応：`AUDIO_ENROLL_*`を小文字にした名前（IDLE→idle … CANCELLED→cancelled）。`reason`は`FAILED`のときだけ付け、それ以外は`null`です。`chime_reason_text()`と同じ語（`too_noisy`・`too_short`・`clipped`・`no_recording`・`unstable`・`background_matches`）に対応させ、検出器の理由がない失敗（通話の開始、取り込みの途切れ）は`no_recording`にします。`busy`は本体が依頼を受けられなかったときだけです。listen中の「もう一度鳴らす」（SHORT・CLIPPED）は契約に項目がないため報告しません。
- 409は連番の食い違いです。同じ報告を繰り返さず、すぐに取得し直し、報告は上の間隔で待ちます。クラウドの`request_seq`が処理済みより小さいときは、クラウドに合わせて処理済みを下げ、その値で報告し直します。
- 再起動：処理済みの連番は保存しません。再起動後に最初に取得した応答が`paired:true`なら、その`request_seq`を処理済みとして採用します。古い開始の依頼が再起動で再実行されないためで、再起動の直前に出た依頼は実行されません（アプリから出し直す）。同じ起動の中で先に`paired:false`を受けてから`paired:true`になったときは、ペアリングの直後の依頼を実行するため、最初の応答の依頼も新しい依頼として扱います。
- 登録は動作モードによらず使えます（停止を含む）。同期処理は`device_mode`を見ません。通話の開始は`audio_app`が登録を失敗にし、通話が終わってから報告します。

ホストテスト（`tests/chime_enroll_protocol_test.c`、`tests/chime_enroll_sync_test.c`）は、模擬のHTTPと音声タスクで、解析、取得の間隔、連番の重複排除、開始と中止、busyでの拒否、段階の即時報告と再送、409、未ペアでの取得、再起動後の連番を確かめます。ESP32-S3 向けのビルド、QEMU、実際のサーバーと実機での登録の流れは、まだ確かめていません（#48）。

### 停止モードで応答しなかった来客の記録

停止モードでチャイム検知か手動の通話要求を捨てたとき、その来客を`PUT /functions/v1/device/visits/<uuid>`で記録します（`docs/spec.md` 5.1）。送る本文は`{"status":"missed","end_reason":"mode_off","mode":"off","chimed_at":"<UTC ISO 8601>"}`だけです。`chimed_at`は捨てた時点のNTP時刻です。`visit_report.c`が実装します。

- 時計が未同期（2024-01-01より前）のときは記録せず、ログに残します。偽の時刻は送りません。
- UUIDは本体が作ります。同じ来客の再送はサーバー側で1件のままです。
- 音声タスクは、メモリ上の4件のキューに積むだけで、通信を待ちません。送信はネットワークタスクが1回に1リクエストずつ、通話中以外に行います。
- キューが満杯のときは、新しい来客を捨てます（古い順に送り終えます）。20秒以内の続けてのチャイムは、通話後の待機と同じく1人の来客として数えます。
- 失敗は10秒から始めて60秒まで間隔を延ばし、1件につき最大6回送ります。それでも届かない件は捨てます。400番台（408、429を除く）は同じ本文では成功しないため、すぐ捨てます。
- キューは再起動で消えます。電源断をまたいで残す永続キューは、Issue #44の範囲で、未実装です。
- チャイム検知は、Wi-Fiと時計が使えない間は始まらないため、その間の停止モードのチャイムは記録されません。
- アプリの履歴一覧は`missed`を表示しません。この記録で届くのは、来客時のプッシュ通知までです。

ホストテスト（`bash run.sh test`の`visit_report`）とDBテストで確認した範囲です。実機のXIAOと実際のSupabaseでの動作は未確認です。

### 通話の順序と復旧

v2ではAPIのWSS接続と`ready`を確認してから通話ボタンを押し、ボタンが戻った後にエージェントを開始します。APIに接続できない場合は、ボタンを押さずにチャイム検知を再開します。従来のv1は通話ボタンを押した後に接続します。

通話ボタンの操作開始から50秒で通話を打ち切り、操作後20秒は新しい通話を受け付けません。終話を確認できなかった場合、開始と終了に別々のボタンを使う構成では、10秒、20秒、以後30秒の間隔で終了ボタンを再試行します。終了ボタンの操作が済み、録音の再開だけに失敗した場合は、サーボを動かさずに再開を試みます。

開始と終了に同じボタンを使う構成では、再押下による通話開始を避けるため自動で押し直しません。親機を手動で終話してからUSB調整画面、または`@confirm`で待機状態を確認します。プッシャー設定の適用待ちやサーボの要確認状態も、自動復旧では解除しません。

本体が確認するのはサーボの動作完了です。実際に親機が終話することや、押下中のサーバー接続が保たれることは、実機で未確認です。

### USB調整画面

`python3 calibration_ui/server.py --serial-port /dev/cu.usbmodem1101` を実行し、`http://127.0.0.1:8767` を開きます。あとは画面の順に進めます。

どの画面でも右側に 3D モデルが出ます。上のバーでインターホンの機種と外装を選びます。モデルは本体のログと設定値で動くので、サーボの押下、呼び出し、再生、聞き取りがそのまま見えます。その下に、部品がキーや画面、充電台に当たらないかを計算して出します。機種の外形は公開値で、キー位置は推定です。実測したら「寸法とキー位置を変える」に入れてください。機種は `calibration_ui/scene/monban_scene.js` の `INTERCOMS` に足すと増やせます。`rough` の付いた機種は、`coverage.md` の外形とキーの説明だけから配置を仮置きしています。縦に串を通す Windea-R と Windea D、キーの情報がない機種はまだ入っていません。外装は同じファイルの `DESIGNS` です。

| 画面 | できること |
|---|---|
| 仮想ボード | `bench` と `qemu ui` で出る。チャイムや違う音を鳴らし、通話を通しで試す。実機の接続先では出ない |
| テスト | `run.sh` の `test`、`e2e`、`build`、`qemu` を実行し、結果とログを見る |
| 動作確認 | 通信、マイク、スピーカー、サーボ、チャイム、通話を順に確かめる。音と動きは「聞こえた」「動いた」で答える |

## チャイムの登録と検出

設計は [`docs/specs/chime-detection/design.md`](../../docs/specs/chime-detection/design.md) にあります。ニューラルネットは使わず、登録した 1 つの音とのテンプレート照合です。

登録の手順（`e`、Web UI の「チャイム」画面、`audio_app_enroll_start()` のどれでも同じ）：

1. 2 秒間静かにする。本体が周りの音を測り、ゲート（周りの音の 4 倍、最小 80）を決める。うるさすぎると中止する。
2. 親機のチャイムを 1 回鳴らす。0.5 秒静かになるまでを録る。4 秒を超えて鳴り続けたら先頭の 3 秒を使う。0.2 秒未満か音割れが 1% を超えたら、もう一度鳴らすよう求める。
3. 本体が録った音を揺らした版（半フレームずらし、-6 dB、雑音の追加、±6% の伸縮）と照合してしきい値を決め、測った周りの音がその音に一致しないことを確かめる（約 3 秒）。通れば保存し、すぐに検出を始める。確認のための 2 回目は鳴らさない。

検出は 20 ms ごとに、テンプレートの末尾まで一致した時点で判定します。音の終わりの静けさは待ちません。検出後 3 秒は再検出しません。保存形式は `AUDIO_MODEL_VERSION 2` で、以前の 3 回登録のモデルは読み込まれず、登録し直しになります。アプリから登録を始める経路は、次の「アプリからのチャイム登録」に書いた依頼の取得と進捗の報告です（Issue #62）。

評価は合成音だけで行っています。

```bash
bash run.sh eval            # 20 家庭分の合成チャイムで、新旧の検出率と誤検出数を表にする
bash run.sh eval --seed 5000  # 定数の調整に使っていない家庭で確かめる
bash run.sh wav enroll.wav target.wav   # 16 kHz・モノラル・16 bit の WAV。enroll.wav は先頭 2 秒が静かな背景
```

調整に使ったシード 1000 では、SN 比 10 dB 以上の正例で検出率 99% 以上、負例の誤検出 0 件でした。調整に使っていないシード 5000 では、半音違いの音を含む別のチャイムを 1 件誤検出しました。SN 比 5 dB の検出率は 27〜47% です。結果の表と決めた定数は設計書にあります。**これは合成音での結果で、実際の親機・マイク・部屋での性能ではありません。** 実機の録音での確認は #48 で行います。

## テスト

```bash
bash run.sh test
```

移植元のホストテストに相当するものです。C と C++ は AddressSanitizer と UndefinedBehaviorSanitizer を付けて動かします。

```bash
bash run.sh e2e
```

`backend/voice-agent` の本物の `/api/relay` v2 のコードに、このファームウェアの通話処理をそのままつなぐテストです。通常の会話、チャイムから始まる通話、途中で止めた通話、サーバーに届かないとき、API キーを拒否されたときを確かめます。置き換えているのは次の部分だけです。

- 音声認識、応答生成、音声合成
- TLS（平文の TCP でつなぐ）
- マイク、スピーカー、PWM、NVS、フラッシュ

```bash
bash run.sh qemu
```

ESP32-S3 用にビルドしたバイナリを、Espressif の QEMU で起動してシリアルで操作するテストです。実機向けのビルドとの違いは、QEMU に合わせた次の 3 点だけです。

- 出力先が USB CDC ではなく UART
- フラッシュが QIO ではなく DIO
- USB 専用のタイムアウト設定 1 行を除く

QEMU には Wi-Fi と I2S のデータがないため、ネットワークと音はこのテストでは確かめられません。

| アンプ | MAX98357A が鳴るか、SD_MODE の切り替え、切り替え時の雑音、音量 70% が適切か |

| サーボの向き | 既定では通話と終了のパルスが逆向きに動く。機構に対して正しいか |

| フラッシュ | 消去中にマイクの取り込みが途切れないか（1 セクターごとに消去している） |

| 動作モードとheartbeat | 実サーバーでのモード取得、停止モードで実際のチャイムに応答しないこと、再起動後と通信断のときに最後の正常値で動くこと、heartbeatがアプリの接続切れ通知と一致すること。適用モードの報告も、ホストテストの模擬サーバーだけで、実サーバーの`devices.applied_mode`への反映は未確認。ホストテストは模擬のHTTPとNVSで確かめただけ |
| アプリからのチャイム登録 | 実サーバーの`chime-enrollment`と`chime-enrollment-status`との往復、実機のマイクでの登録、通話の開始での失敗、再起動後に古い依頼が再実行されないこと。ホストテストの模擬HTTPと模擬の音声タスクで確かめただけで、ESP32-S3 向けのビルドも未実行（#62、#48） |

| v1 の中継 | `VOICE_RELAY_PROTOCOL=1` は C のテストだけで、LiveKit とはつないでいない |

## 移植元から変えたこと

- サーボの PWM は 16 bit から 14 bit にしました。ESP32-S3 の LEDC は 14 bit までです。
- 再生後に録音を始めるまでの待ちは 250 ms から 500 ms にしました。`docs/spec.md` 5.1 の値です。
- mbedTLS のこのビルドは証明書の有効期限を見ないため、接続後に NTP の時刻と照合しています。
- 音量の既定は 70% です。5 V のアンプはフルスケールで 1 W のスピーカーの定格を超えるおそれがあるためです。
- チャイムを検知したら、録音の残りを待たずに通話を始めます。録音の保存は通話が終わってから行います。フラッシュの処理で通話の音が途切れないようにするためです。

## 未実装

E84 と M5 にもなく、`docs/spec.md` だけにある機能は移していません。

- 定型音声 U01、X01（5.7）
- 本体から Supabase の Edge Function への送信（5.5）
- 通話後 20 秒のチャイム検知の停止（5.1）
- 停止モードで応答しなかった来客の記録は、メモリ上のキューまで実装済みです（上の節）。再起動をまたぐ永続化は未実装です（Issue #44）
- 適用モードの報告（`PUT /mode-status`）は、実機と実サーバーではまだ確かめていない（上の節）。取得した時刻の報告は未実装で、通信の生存は heartbeat だけが伝える

押す時間の上限は M5 と同じ 2000 ms です。`docs/spec.md` 4.4 は 500 ms を上限としているので、VS-MGE20 で使うときは 500 ms 以下に合わせてください。
