# MONBAN ファームウェア（XIAO ESP32S3）

[![XIAO firmware](https://github.com/jphacks/tka_2601/actions/workflows/xiao-firmware.yml/badge.svg)](https://github.com/jphacks/tka_2601/actions/workflows/xiao-firmware.yml)

E84 と M5Stack に分かれていた機能を、Seeed XIAO ESP32S3（無印）1 枚で動かすファームウェアです。追加基板（MAX98357A アンプ、LMD3526 PDM マイク）を前提にしています。基板の設計データはまだこのブランチにないので、ピン配置は下の表を見てください。

**実機ではまだ一度も動かしていません。** 確かめたことと確かめていないことは「[確認の状況](#確認の状況)」に書きました。

## 実機なしで試す

XIAO がなくても、次のコマンドで試せます。リポジトリのどこからでも `bash firmware/xiao/run.sh ...` で実行できます。

| コマンド | 確かめること | 必要なもの | 時間の目安 |
|---|---|---|---|
| `bash run.sh test` | 各部のホストテストと Web UI のテスト | clang、Python 3、Node.js | 1 分 |
| `bash run.sh e2e` | 本物の `/api/relay` のコードと、ファームウェアの通話処理をつないだ会話 | 上に加えて uv | 初回は依存の取得が要る |
| `bash run.sh browser` | 本物の Chromium で Web UI を開き、チャイム登録から通話まで実際にクリックして通す | e2e と同じ。初回は Chromium の取得（約 100 MB）が要る | 2 分 |
| `bash run.sh qemu` | ESP32-S3 用のバイナリを QEMU で起動し、シリアルで操作 | arduino-cli、Python 3 | 初回は ESP32 コアの取得（数 GB）が要る |
| `bash run.sh bench` | ブラウザで Web UI を操作する。通話まで動く | e2e と同じ | 起動まで数十秒 |
| `bash run.sh qemu ui` | ブラウザで Web UI を操作する。相手は QEMU 上の ESP32-S3 用バイナリ | qemu と同じ | 起動まで 1 分ほど |

Web UI を試す 2 つの違いは次のとおりです。`bench` は Mac 向けにコンパイルしたファームウェアで、音声は模擬なので通話まで進みます。`qemu ui` は実機用のバイナリそのものですが、QEMU に Wi-Fi と音声がないので、サーボの調整や保存までしか動きません。QEMU 自体に Web UI はなく、どちらも `http://127.0.0.1` の同じ画面を使います（`bench` は 8767 番、`qemu ui` は 8768 番）。

QEMU の本体は初回に公式リリースから `.host-build/` へ取得し、SHA-256 を照合します。対応するのは macOS と Linux です。Windows は WSL で動かしてください。

GitHub では、`firmware/xiao` に触れる PR ごとに `test`、`e2e`、`browser`、ビルド、`qemu` が自動で動きます。手で動かすときは Actions の「XIAO firmware」から Run workflow を押します。

## 機能

| 機能 | 内容 | 移植元 |
|---|---|---|
| チャイムの登録と検知 | ログメル特徴と DTW。環境音 5 秒、3 回の登録、別の 1 回の確認 | `firmware/psoc6` |
| 登録の保存 | 2 MiB の専用パーティションに 2 つ写しと CRC で保存 | `firmware/psoc6` |
| 録音の保存と送信 | HTTPS で WAV を送り、同じイベント ID の ACK を待つ。送信先を設定したときだけ動く | `firmware/psoc6` |
| 会話 | `/api/relay` と WSS で接続。16 kHz、16 bit、モノラルの PCM を 20 ms（640 B）ごとに送受信 | `PSOC_Edge_E84` |
| 再生 | I2S で再生し、DMA が空になってから完了を報告 | `M5Stack_Basic_E84_Link` |
| サーボ | 押して戻す動作、角度と時間の調整、USB からのテスト | `M5Stack_Basic_E84_Link` |
| 確認と調整の Web UI | Mac の `calibration_ui/` が USB シリアルで本体とやり取りする | `M5Stack_Basic_E84_Link` を作り直した |

E84 と M5 の間の UDP 通知と TCP 中継（DVS1）は削除しました。通話の処理が、サーボとスピーカーを直接動かします。

サーボは 1 が通話、2 が終了、3 が解錠です。解錠のサーボは USB のテストと角度調整でだけ動き、通話からは動きません。中継サーバーに解錠の指示がなく、`docs/spec.md` 5.6 が「鍵やドアを開ける約束をしない」と決めているためです。

## ピン配置

`board_pins.h` に定義しています。

| XIAO | GPIO | つなぐ先 |
|---|---|---|
| D0 | 1 | アンプ DIN |
| D1 | 2 | アンプ LRCLK |
| D2 | 3 | アンプ BCLK |
| D3 | 4 | マイク DATA |
| D4 | 5 | マイク CLK |
| D5 | 6 | アンプ SD_MODE（Low で停止、駆動しないと (L+R)/2 のモノラル） |
| D8 | 7 | サーボ 1（通話） |
| D9 | 8 | サーボ 2（終了） |
| D10 | 9 | サーボ 3（解錠） |

## ビルドと書き込み

`arduino-cli` と esp32 コア 3.3.8 を使います。`arduino-cli` は PATH にあるものか Arduino IDE に入っているものを使い、コアがなければ初回に入れます。パーティションは `partitions.csv` のとおりで、PSRAM は OPI にしています。

```bash
bash run.sh build
```

```bash
bash run.sh upload /dev/cu.usbmodem1101
```

書き込みは XIAO 自身の USB-C から行います。追加基板の USB-C は電源専用で、書き込むときは抜いておきます。

## 設定

設定を変えたら、ビルドと書き込みをやり直します。作られるヘッダーは Git の対象外です。

Wi-Fi の設定です。iPhone のテザリングでは `--hotspot` を付けます。

```bash
python3 configure_wifi.py
```

サーバーの設定です。`.env.example` を `.env` にコピーして `DOOR_API_KEY`、`DOOR_RELAY_MODE`、`DOOR_DEVICE_KEY` を入れてから実行します。

```bash
python3 configure_api.py
```

録音の送信先は任意です。設定しない間は、録音をフラッシュに保存しません。`docs/spec.md` 5.2 と 10 章で扱いが未定のため、既定で切っています。

```bash
python3 configure_upload.py --ca /path/to/receiver-root-ca.pem
```

## 最初に動かす手順

`python3 calibration_ui/server.py --serial-port /dev/cu.usbmodem1101` を実行し、`http://127.0.0.1:8767` を開きます。あとは画面の順に進めます。

どの画面でも右側に 3D モデルが出ます。上のバーでインターホンの機種と外装を選びます。モデルは本体のログと設定値で動くので、サーボの押下、呼び出し、再生、聞き取りがそのまま見えます。その下に、部品がキーや画面、充電台に当たらないかを計算して出します。機種の外形は公開値で、キー位置は推定です。実測したら「寸法とキー位置を変える」に入れてください。機種は `calibration_ui/scene/monban_scene.js` の `INTERCOMS` に足すと増やせます。`rough` の付いた機種は、`coverage.md` の外形とキーの説明だけから配置を仮置きしています。縦に串を通す Windea-R と Windea D、キーの情報がない機種はまだ入っていません。外装は同じファイルの `DESIGNS` です。

| 画面 | できること |
|---|---|
| 仮想ボード | `bench` と `qemu ui` で出る。チャイムや違う音を鳴らし、通話を通しで試す。実機の接続先では出ない |
| テスト | `run.sh` の `test`、`e2e`、`build`、`qemu` を実行し、結果とログを見る |
| 動作確認 | 通信、マイク、スピーカー、サーボ、チャイム、通話を順に確かめる。音と動きは「聞こえた」「動いた」で答える |
| サーボ | 通話、終了、解錠の角度と時間を合わせて本体に保存する。ホーンを外した状態で始める |
| 音 | マイクの音量を見ながら話し始めの音量を決める。スピーカーの音量とチャイムの判定幅を変える |
| チャイム | 案内に従って登録する。保存領域が未初期化なら、そのときだけ初期化のボタンが出る |
| テスト通話 | 通話を始める、止める。進行状況、会話、本体のログを見る |

実機がなくても、この画面を次のコマンドで動かせます。本物のファームウェアのコードと中継のコードを Mac 上で動かします。マイク、スピーカー、PWM は模擬で、音声 AI は決まった応答に置き換えています。チャイムは画面のボタンで鳴らします。

```bash
bash run.sh bench
```

## シリアルのコマンド

1 行に 1 つ送ります。

| 入力 | 動作 |
|---|---|
| `h` | 一覧 |
| `s` | 状態 |
| `c` / `q` | 通話を始める / 止める |
| `e` / `x` | チャイム登録を始める / 登録とサーボのテストを止める |
| `r` | 5 秒録音して送信待ちにする（送信先の設定が必要） |
| `1` `2` `3` | サーボのテスト（通話、終了、解錠） |
| `t` | スピーカーで 1 kHz を 1 秒鳴らす |
| `l` | 3 秒録音してそのまま再生する。保存はしない |
| `m` | マイクの音量と検知の状態 |
| `n` `a` `w` `u` | Wi-Fi、サーバーの HTTPS、音声の WSS、USB の確認 |
| `@get` `@begin` `@set` `@angles` `@time` `@test` `@stop` `@mirror e` `@save` `@cancel` | サーボの調整。M5 と同じ形で、`u`（解錠）を足した |
| `@tune get`、`@tune volume 0..100`、`@tune gate 30..32767`、`@tune margin 50..200` | 音量、話し始めの音量、チャイムの判定幅。すぐに NVS へ保存する |
| `FORMAT_AUDIO_STORAGE` | 保存領域を消去して初期化する。Web UI からは未初期化のときだけ送れる |

## テスト

```bash
bash run.sh test
```

移植元のホストテストに相当するものです。C と C++ は AddressSanitizer と UndefinedBehaviorSanitizer を付けて動かします。

```bash
bash run.sh e2e
```

`backend/voice-agent` の本物の `/api/relay` v2 のコードに、このファームウェアの通話処理をそのままつなぐテストです。通常の会話、チャイムから始まる通話、途中で止めた通話、サーバーに届かないとき、API キーを拒否されたときを確かめます。置き換えているのは次の部分だけです。

- 音声認識、応答生成、音声合成
- TLS（平文の TCP でつなぐ）
- マイク、スピーカー、PWM、NVS、フラッシュ

```bash
bash run.sh qemu
```

ESP32-S3 用にビルドしたバイナリを、Espressif の QEMU で起動してシリアルで操作するテストです。実機向けのビルドとの違いは、QEMU に合わせた次の 3 点だけです。

- 出力先が USB CDC ではなく UART
- フラッシュが QIO ではなく DIO
- USB 専用のタイムアウト設定 1 行を除く

QEMU には Wi-Fi と I2S のデータがないため、ネットワークと音はこのテストでは確かめられません。

## 確認の状況

### 確かめたこと

- `esp32:esp32:XIAO_ESP32S3` 向けのビルド（プログラム 32%、静的 RAM 60%）
- `bash run.sh test`：すべて成功
- `bash run.sh e2e`：5 件すべて成功
- `bash run.sh qemu`：すべて成功。確かめたのは次の項目です。
  - 実バイナリの起動、PSRAM、パーティション、全タスクの起動
  - PDM、I2S、LEDC の各ドライバーが設定を受け付けること
  - 3 つのサーボの動作と、シリアルのコマンド
  - NVS への保存と 2 MiB の領域の初期化、電源を入れ直した後の復元
  - ネットワークやマイクがないときに固まらず失敗を報告すること
- `bash run.sh browser`：Chromium（Playwright）で、全画面の表示と 3D の描画、機種と外装の切り替え、実測値の入力、接続とスピーカーとサーボの確認、チャイム登録、チャイムからの通話、通話の停止、テストの実行と停止、狭い画面幅を確かめ、コンソールにエラーがないことを確認
- `bash run.sh bench` とブラウザで、Web UI の主な操作（機種と外装の切り替え、まとめて確認、サーボのテスト、チャイム登録、チャイムからの通話とその間の 3D の動き、違う音の判定、テストの実行）

### 実機で確かめていないこと

下の項目は、どれも動作を確認していません。

| 項目 | 確かめること |
|---|---|
| 起動 | QIO フラッシュと USB シリアルでの起動（QEMU は DIO と UART で確認） |
| Wi-Fi と時刻 | 接続、再接続、NTP の同期、テザリングでの接続 |
| TLS と WSS | 実サーバーとの証明書の検証、有効期限の確認、接続中のメモリの余裕 |
| マイク | LMD3526 から正しい音が取れるか。特に左チャンネルの指定と 2.048 MHz のクロック |
| アンプ | MAX98357A が鳴るか、SD_MODE の切り替え、切り替え時の雑音、音量 70% が適切か |
| サーボ | FS0307 が 1000〜2000 µs で必要な角度に動くか（M5 で使った SG90 の値のまま）。14 bit の PWM の精度。押す角度の既定 30° でキーが押せるか（ラック 2.4 mm、計算のみ） |
| 電源 | サーボが動くときと大きな音のときに電圧が下がらないか |
| 同時動作 | Wi-Fi、TLS、マイク、再生を同時に動かしたときに音が途切れないか |
| フラッシュ | 消去中にマイクの取り込みが途切れないか（1 セクターごとに消去している） |
| チャイム | 実際の呼び出し音での取り逃しと誤検知。しきい値は初期値のまま |
| 話し始めの判定 | `VOICE_RMS_GATE` の 600 は E84 のマイクの値で、このマイクでは測っていない |
| 回り込み | スピーカーとマイクが同じ外装に入ったときの影響 |
| 通話全体 | 実際のインターホンと実サーバーでの連続した会話 |
| 録音の送信 | 実際の受信サーバーへの送信 |
| v1 の中継 | `VOICE_RELAY_PROTOCOL=1` は C のテストだけで、LiveKit とはつないでいない |

## 移植元から変えたこと

- サーボの PWM は 16 bit から 14 bit にしました。ESP32-S3 の LEDC は 14 bit までです。
- 再生後に録音を始めるまでの待ちは 250 ms から 500 ms にしました。`docs/spec.md` 5.1 の値です。
- mbedTLS のこのビルドは証明書の有効期限を見ないため、接続後に NTP の時刻と照合しています。
- 音量の既定は 70% です。5 V のアンプはフルスケールで 1 W のスピーカーの定格を超えるおそれがあるためです。
- チャイムを検知したら、録音の残りを待たずに通話を始めます。録音の保存は通話が終わってから行います。フラッシュの処理で通話の音が途切れないようにするためです。

## 未実装

E84 と M5 にもなく、`docs/spec.md` だけにある機能は移していません。

- 定型音声 U01、X01（5.7）
- 本体から Supabase の Edge Function への送信（5.5）
- 通話後 20 秒のチャイム検知の停止（5.1）

押す時間の上限は M5 と同じ 2000 ms です。`docs/spec.md` 4.4 は 500 ms を上限としているので、VS-MGE20 で使うときは 500 ms 以下に合わせてください。
