# 作業計画（Hack Day 2日間・3〜5人）

仕様は [spec.md](spec.md) を参照する。時刻は開始からの経過時間（H+n）で書く。実際のスケジュールに合わせて読み替える。

## 1. 着手前にやること

Hack Day 当日はツールのインストールだけで数時間を失う。開発ルール上許される範囲で、次を事前に済ませる（コードの事前作成が可能かは JPHacks の規約を確認する）。

| 項目 | 担当 | 完了条件 |
|---|---|---|
| センサーボードの型番の確認（[spec.md 4.3](spec.md#43-支給品の型番の候補と影響)） | P1 | AI Kit か PROTO キットかが分かり、レーダーを使えるかが決まっている |
| 買い出し（[spec.md 9章](spec.md#9-部品表bom)） | 全員 | スピーカー（USB スピーカーか秋月電子の組み合わせ）、1000 µF の電解コンデンサ、ゴム・スポンジが手元にある |
| VS-SGE20LA の準備 | P2 | 親機を充電し、玄関子機に電池を入れ、呼出音を音1・音量大にしてある |
| ModusToolbox のインストール | P1, P2 | 各キットで LED 点滅のサンプルが書き込める |
| DEEPCRAFT Studio のインストール | P1 | 動く PC（Windows の可能性あり）が決まっている。だめなら Edge Impulse のアカウントを作る |
| door API の疎通確認 | P3 | API キーでセッションを作り、録音した音声を送って返答音声が返る |
| door API の担当者との相談（[spec.md 5.8](spec.md#58-door-api-への追加要望)） | P4 | 追加要望のうち Hack Day までに入るものが分かっている |
| 定型音声の生成（[spec.md 5.7](spec.md#57-定型音声)） | P4 | 4つの WAV が door_neutral の声でそろっている |

## 2. 役割分担

### 5人の場合

| ID | 担当 | 主な成果物 |
|---|---|---|
| P1 | PSoC 6（耳・目） | チャイム検知モデル、訪問者の声を PC へ送る処理、レーダー在室判定 |
| P2 | PSOC Control C3 と機構（手） | MG996R 2つの押下ファーム、5V 給電の配線、押下アーム、ブラケットとガード板 |
| P3 | 音声ブリッジ | 状態機械、スピーカーでの再生、door API クライアント、障害時の定型応答 |
| P4 | 会話の品質 | `house_rules`、評価データ、会話の試験（T5, T6）、door API 担当者との調整 |
| P5 | 通知とデモ | モード切替の Web 画面、ntfy 通知、デモ台本、スライド、README、動画 |

### 3〜4人の場合

- 3人: P1、P2 はそのまま担当し、残る1人が P3 と P4 を兼ねる。P5 のうち Web 画面は設定ファイルの書き換えで代え、発表準備は Day 2 の後半に全員で分担する。
- 4人: P4 と P5 を1人が兼ねる。

## 5. リスクと対策

最初の3時間で R1〜R3 と R8 を判定し、ダメなら代替案に切り替える。

| ID | リスク | 影響 | 対策 | 代替案 |
|---|---|---|---|---|
| R1 | 親機のスピーカー音が小さい、または歪み、文字起こしが崩れる | 会話不能 | PSoC 6 のマイクを親機スピーカーに寄せ、ゲインを調整する。親機の音量を最大にする | ノート PC の内蔵マイクを親機スピーカーに近づける |
| R2 | サーボの力が強すぎて親機を傷める、または押下がずれる | 親機の破損、応答不能 | ゴム先端、ファームの角度制限、機械的なストッパー。押下角は少しずつ合わせる | キットの SG90 に替える（力が弱い） |
| R3 | 会場から door API までが遅い、または labpc が止まる | 会話不能 | 会場で応答時間を測る。スマホのテザリングを用意する。担当者と停止時の連絡方法を決める | 定型音声だけで応答する（FALLBACK） |
| R4 | LLM が不在や住人の情報を話す | 安全上の問題 | `house_rules` と意地の悪い発話の試験 | 該当する返答を出した場合は、`house_rules` を直すまで外出モードを使わない |
| R5 | 自分の返答の回り込みで会話が乱れる | 会話が途切れる | 再生中はマイクの音を送らない | barge-in を切る設定をサーバーに頼む |
| R6 | チャイムの誤検知、または会場の雑音で検知できない | 無人の玄関に応答する、またはデモ失敗 | 連続フレームで判定する。会場の雑音を学習データに足す | 手動トリガーを用意し、使った場合は発表でその旨を明言する |
| R7 | ModusToolbox や DEEPCRAFT の環境構築に手間取る（DEEPCRAFT は Windows 専用の可能性） | PSoC 側の遅延 | 事前インストール。Windows 機を確保する | Edge Impulse に切り替える |
| R8 | PSoC 6 から PC へ訪問者の声を送れない | PSoC 6 のマイクで会話できない | Day 1 の前半に送る方法を決める | ノート PC の内蔵マイクを使う |
| R9 | サーボの電流で C3 の 5V が下がり、リセットする | 押下の途中で止まる | 2つを同時に動かさない。押し付け続けない。電解コンデンサを付ける | サーボの電源を USB 充電器などの別の 5V に分け、GND を共通にする |
| R11 | 親機の自動切替でデバイスの声が途切れる、または玄関子機と近すぎてハウリングする | 会話が乱れる | スピーカーの音量とマイク穴との距離を調整する。デモでは玄関子機を離して置く | プレストークを使う（[spec.md 3.7](spec.md#37-ハンズフリー親機は半二重として扱う)） |
| R10 | センサーボードにレーダーがない（PROTO キットだった） | 在室判定ができない | 手動のモード切替で代える | なし（機能を削る） |

## 6. デモ構成

- 机の上に VS-MGE20（充電台に立てる）を置き、本デバイスを取り付ける。玄関子機 VS-VG562 はハウリングしないよう離れた場所に置く。
- 審査員の見える画面に、状態遷移と door API の文字起こし・返答を表示する。
- 1本目（おまかせモード）: 配達員役が子機を押し「ヤマト運輸です、お荷物のお届けです」と話す。デバイスが置き配を頼んで終話し、スマホに通知が届く。
- 2本目（同じモード）: 配達員役が「クール便なので置けないんです」と断り、デバイスが不在票を頼む。
- 3本目（外出モード）: 訪問者役が「〇〇さん、今お留守ですか」と聞き、デバイスが不在を明かさずに応じる。
- 4本目: ネットワークを切った状態でチャイムを鳴らし、定型音声で応答して終話することを見せる。
- 発表では、不在時に置き配を頼まない理由（[spec.md 3.5](spec.md#35-置き配を頼むのは在宅時に限る)）を、配送の運用を調べたうえでの設計判断として説明する。
