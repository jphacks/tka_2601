# E84・M5の音声会話

## 実装した流れ

チャイム検知、またはE84のUARTで `c` → M5の接続確認 → 設定した時間だけ待つ → 通話ボタンを1回押す → 待機位置へ戻してPWM停止 → API接続・agent開始 → 挨拶 → 来訪者の音声 → ASR/LLM/TTS → M5再生 → 次の録音、を繰り返します。会話終了時は最後の音声の再生後に終了ボタン用サーボを動かします。`q` は録音・再生を止めて通話終了を要求します。

E84がWi-Fi/API認証と会話状態を管理します。CM55はPDM取得・チャイム照合・発話区切り、CM33はWSSとM5へのTCP転送を担当します。クラウドへは既存の `/api/relay` にJSON制御と生PCMを送り、M5へは従来のDVS1を送ります。サーバーのv2経路は既存DoorAgentを同じLiveKit Agents SDKのAgentSession内で動かします。音声認識は発話確定後に既存STTクライアントで実行し、応答生成・TTS・住人ルールを再利用します。ブラウザーと旧relayのLiveKitルーム経路は維持します。

音声は16kHz/16bit/mono。20ms（640バイト）単位で送信し、発声後の無音1.2秒または30秒で区切ります。30秒には200msの先行バッファと末尾無音も含みます。無音だけなら音声フレームを送信せず待ちます。最初の発話待ちは60秒です。サーバーの通話上限は既存の `DOOR_RELAY_MAX_SESSION_SECONDS`（既定120秒）に従います。端末にも切断時の上限がありますが、サーバーの期限を延長するものではありません。

発声判定はRMSを使います。`source/voice_settings.h` の `VOICE_RMS_GATE`（既定600）以上が60ms続くと開始し、その半分未満の音量が1.2秒続くと終了します。学習済みVADではないため、設置場所の雑音・マイク音量で調整してください。録音と返答の同時進行・割り込み発話には対応しません。

CM55→CM33は64フレーム、1.28秒分の共有リングです。共有領域の使用量は約233KBで256KiB以内です。30秒分全体をE84に保持しません。サーバーはASRのため1発話を最大960KBまで保持します。応答待ち・再生中のマイクサンプルは捨て、次の録音に混ぜません。

## サーバーへ反映

既定の `VOICE_RELAY_PROTOCOL=1` は、GitHubの [`backend/voice-agent/door_backend/relay.py`](https://github.com/jphacks/tka_2601/blob/main/backend/voice-agent/door_backend/relay.py) と稼働中サーバーの既存仕様に合わせています。サーバーを変更せず、認証付き `WSS /api/relay` に `start` JSONと16kHz PCMを送り、`ready`、PCM、`agent_state`、`transcript` を受け取ります。`POST /api/connect` はブラウザーのLiveKit用で、E84の接続先には使いません。OpenAPIにWebSocketは表示されないため、貼り付けられたOpenAPIだけで会話仕様を判断しないでください。

実サーバーでは `agent_state: listening` の後も低い非ゼロPCMが続くことを確認しています。v1接続ではこの状態通知から500msの末尾音声を受けた後にM5へ `OUTPUT_END` を送り、それ以後の待機PCMを捨てます。単なるPCMの途切れだけでは終了しません。M5から実再生完了が戻り、250msの残響待ちを終えてから次の録音を許可します。LiveKitのVADがE84の無音1.2秒より先に返答を始めた場合も、録音を止めて再生へ切り替え、残った入力を次の発話に混ぜません。AIの確定文字起こしに「失礼いたします」が含まれる場合、最後の再生後に終了操作を行います。手動終了はUART `q` です。 ローカルRMSが拾った音をサーバー側VADが認識しない場合に備え、入力終了後もagentが聞き取り状態のまま20秒経過するとマイクを再待機します。`thinking` や再生中には再待機せず、遅れて返答が始まった場合も直ちに録音を止めます。認識内容・agent状態・既知のエラーコードはUSB/Web UIへ表示します。

ローカルにある拡張版バックエンドへ反映する場合だけ、`VOICE_RELAY_PROTOCOL=2` を指定できます。その場合は明示的な `output_end` / `listen` / `call_end` とフレームACKを利用し、バージョンなしreadyを拒否します。v2のローカル実装が存在するだけでは、稼働中サーバーの更新を意味しません。

E84の `.env` にAPI設定に加えて `DOOR_RELAY_MODE=omakase` と `DOOR_DEVICE_KEY` を設定します。デバイス鍵はSupabaseの住人設定取得・履歴保存用で、FastAPI認証の `DOOR_API_KEY` とは別です。v1では鍵が空なら、バックエンド付属シミュレーターと同様に未登録の診断用IDで通話できます。この場合、住人設定の取得と履歴保存はできません。v2では鍵を必須にしています。キーを設定した後、設定生成とビルドを行います。M5との通信は設定済みUDPポート+1（標準8769/TCP）と、同じペアリングトークンを使います。

## サーボのサンプル

通話用GPIO26、終了用GPIO17の2台構成です。標準の通話動作は3秒待機→押下位置を0.3秒保持→待機位置へ1秒戻してPWM停止です。角度・通話前待機・通話と終了の押下時間・復帰時間はWeb UIで保存できます。旧版の保存済み角度は引き継ぎます。通話ボタンの操作完了通知を受け取るまで、E84はWSS接続とagent開始JSONを送りません。実サーボ用の電源と共通GND、角度調整は[M5 README](../../M5Stack_Basic_E84_Link/README.md)を参照してください。センサーはなく、完了通知はPWM操作の完了を意味します。

未配線でもサンプルPWMコードは動作します。ボタンを人が押して連携を確認する場合は、M5の `servo_config.h` で `M5_SERVO_ENABLED 0`、`M5_SERVO_MANUAL_TEST 1` を明示します。開始はM5のA、終了はCで操作完了を通知します。

## 順に確認すること

1. E84の `t` で従来のUDP往復を確認します。
2. E84の `c` でチャイム検知を省略して通話を開始します。通話用サーボが動くので、取り付け前に角度を確認してください。
3. M5から挨拶が流れ、E84が `M5 playback complete` → `Listening` と表示することを確認します。
4. 話した後に1.2秒黙り、`Input complete` → M5の返答 → 次の `Listening` になることを確認します。
5. 長い発話を30秒で区切ること、返答再生中に録音が開始しないことを確認します。
6. `q` または会話の終了で終了ボタン用サーボが動くことを確認します。
7. 最後に実際のチャイムから開始します。通話中は再検知を抑制します。

切断・PCM欠落・バッファあふれでは不完全な発話を取り消します。M5は音声を停止し、通話押下済みなら終了ボタンを一度押します。E84がM5の終了を確認できない場合は録音を止めたままにします。インターフォンの状態を確認して両ボードをリセットしてください。

SDKのTCP接続確立処理は同期呼び出しで、接続先が応答しない場合はSDKの接続タイムアウトまで待つことがあります。この間は録音を停止し、M5の接続を確認してボタンを操作してからAPIへ接続します。API接続が失敗した場合はM5へ終了操作を要求します。シリアルの `q` は接続呼び出しが戻った時点で処理します。

## 検証範囲

ホストテストでは30秒・1.2秒境界、録音停止、欠落、再生完了の条件、JSON/PCMとDVS1の変換、WebSocket分割、通信切断、サーボ重複抑止を検証します。v1については待機中PCM、発話状態後の末尾音声、M5再生完了待ち、先に返答を始めるサーバーVAD、20msの無音送信も確認します。実機ではE84から実サーバーへの接続とM5での挨拶再生、ch3のマイク入力を確認済みです。位置合わせ後の実機連続通話は別途確認が必要です。

Macから実サーバーのASR・LLM・TTSだけを一往復させる診断もできます。`websocket-client` と `certifi` のあるPythonで、16kHz・16bit・monoの訪問者WAVを渡します。

```sh
python3 tools/relay_smoke_test.py visitor.wav --seconds 60
```

認証はこのE84プロジェクトの `source/api_config.h` を読み、登録住人に紐付かない診断用IDで既存 `/api/relay` へ接続します。サーボ・E84のマイク・M5のスピーカーを経由するテストではありません。空のWAV・全ゼロ音声・30秒を超える音声を拒否し、来訪者の文字起こし・AI文字起こし・返答PCMのすべてが確認できた場合だけ終了コード0になります。2026-10-18に「こんにちは。宅配便です。荷物をお届けに来ました。」から「恐れ入りますが、玄関の前に置いていただけますか。」の返答PCMまで成功しました。

最新TTSは不要な末尾音を除くため返答全体の生成を待ってから音声を流します。今回の更新はこの処理を変更しません。音声の転送・M5での再生はフレーム単位ですが、生成途中からの低遅延再生を保証するものではありません。
